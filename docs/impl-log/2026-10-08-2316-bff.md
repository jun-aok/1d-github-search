# 実装ログ: ログの抽象化、GitHubClient、BFF（Route Handler 2 つ）

- 日時: 2026-10-08 23:16
- 依頼: ループの 2 単位目。`lib/observability/`、`lib/github/`（githubError、GitHubClient、parse、Fake、Http、index）、`lib/api/`（appError、respond、withErrorHandling、handlers）、Route Handler 2 つ、MSW の GitHub ハンドラを TDD で実装し、`e2e/bff-errors.spec.ts`（8 件）を Green にする。
- 結果: 全部できた。`bff-errors.spec.ts` 8 件 Green（desktop プロジェクトのみ実行。mobile 側に bff-errors は無い）。単体テストは 159 → 244 件（85 件追加）。lint・typecheck も通った。E2E の全件は流していない（この単位の対象は `bff-errors` のみ）。

## 迷った点と判断

### 1. `console.ts` の warn の出力先

- 状況: design.md 8 節は「JSON 1 行で標準出力へ。`error` は `console.error`」とだけ書き、warn の出力先が書かれていない。
- 選択肢: (a) `console.log`、(b) `console.warn`。Node では `console.error` と `console.warn` は標準エラー、`console.log` は標準出力。
- 判断: (b)。レベルと出力関数が 1 対 1 で対応し、テストで error 側に漏れていないことも確かめやすい。Docker や Vercel はどちらもログ基盤に流す。
- 実装: `src/lib/observability/console.ts`、`console.test.ts`。
- 確度: 仮（文書の「標準出力」と厳密には食い違う）

### 2. `observability/index.ts` に「環境で選ぶ」分岐を持たせなかった

- 状況: design.md 2 節は `index.ts(環境で選ぶ)`、8 節は「テストでは注入」と書く。選ぶ先は `console` と `memory` の 2 つだが、memory はテストが `Deps` に直接渡す。
- 選択肢: (a) `NODE_ENV === "test"` なら memory を返す分岐、(b) 分岐を持たず console を常に export する。
- 判断: (b)。(a) だと本番コードにテスト用の分岐が入る（design.md 4 節の「本物の実装にテスト用の分岐を入れない」と同じ考え方）。実インフラを入れるときにここを変える、というコメントだけ残した。
- 実装: `src/lib/observability/index.ts`（`logger` と `reporter` を export）。
- 確度: 仮

### 3. `ErrorReporter` の既定実装を `Logger` の上に作った

- 状況: design.md 8 節の実装表に `console.ts` と `memory.ts` しかなく、`ErrorReporter` の既定実装の置き場所が決まっていない。
- 選択肢: (a) `console.ts` に reporter も書く、(b) `errorReporter.ts` に「Logger に error として書く」実装 `createLoggerReporter(logger)` を置く。
- 判断: (b)。JSON 1 行の整形が 1 か所で済み、メモリ版 Logger でそのまま検証できる。例外のメッセージとスタックは `errorName` / `stack` のフィールドとして出す。
- 実装: `src/lib/observability/errorReporter.ts`。`memory.ts` の `createMemoryReporter` は withErrorHandling のテスト用。
- 確度: 確定

### 4. `readJson` の戻り値を Result にした

- 状況: design.md は「`res.json()` を `unknown` で受ける」としか書かない。`res.json()` は本文が JSON でないと例外を投げる。
- 選択肢: (a) `Promise<unknown>` で例外は呼び出し側が捕捉、(b) `Promise<Result<unknown, { message: string }>>`。
- 判断: (b)。3 節の「失敗は Result」に従う。Http では「200 なのに JSON でない」を upstream の `contract` にする。
- 実装: `src/lib/http/readJson.ts`。
- 確度: 確定

### 5. `parse.ts` が `lib/model/zodResult.ts` を import する

- 状況: GitHub の形を確かめる zod の失敗を `ParseError` に詰め替える処理が `parse.ts` にも必要。
- 選択肢: (a) `parse.ts` に同じ詰め替えを複製、(b) モデル内に閉じていた `safeParse`（zodResult.ts）を import。
- 判断: (b)。1 単位目で「`zodResult.ts` は `lib/model/` 内に閉じているので可」と回答があったが、ここから `lib/github/parse.ts`（zod を使ってよい 3 か所の 1 つ）が使うと、閉じていない形になる。複製を避けて import した。ESLint と tsc は通る。
- 実装: `src/lib/github/parse.ts`。
- 確度: 仮（zodResult.ts を「zod を使ってよい場所の共有部品」として扱ってよいかの確認が要る）

### 6. `parse.ts` の 1 段目は「型だけ」を見て、規則はモデルに任せた

- 状況: GitHub の `stargazers_count` などを確かめるとき、`int().min(0)` などの規則を 1 段目に書くか。
- 判断: 書かない。design.md 4 節の「モデルの規則を確かめる場所をモデルのファイル 1 か所に揃える」に従い、1 段目は `z.number()` / `z.string()` / `nullable` のみ。負の star 数は 2 段目（`parseSearchResult`）で `items.0.stars` として落ちることをテストで確かめた。GitHub の項目名の誤りは `items.0.stargazers_count` の形で出る。
- 実装: `src/lib/github/parse.ts`、`parse.test.ts`。
- 確度: 確定

### 7. FakeGitHubClient の `__few__` は 2 ページ目以降を「件数あり・items 空」にした

- 状況: E2E の範囲外ページ（`/?q=__few__&page=3`）は「結果は 2 件 = 1 ページ」「このページには結果がありません」を期待する。design.md 4 節の Fake の説明は「`__few__` → 2 件（1 ページ）」だけ。
- 判断: GitHub の本物（design.md 5 節：200・`total_count` あり・`items` 空）に合わせ、`page > 1` は `totalCount: 2, items: []`。通常キーワードは e2e/README.md の「どのページでも同じ 20 件」に従う。
- 実装: `src/lib/github/fakeGitHubClient.ts`。`rate_limited` の `retryAfter` は 60 に固定。
- 確度: 確定（retryAfter の 60 は仮の値）

### 8. レート制限の `retryAfter` の求め方

- 状況: design.md 4 節は「`retry-after` か `x-ratelimit-reset` までの秒数。0 未満は 0」。1 単位目で「整数秒。BFF 側で切り上げる」と回答済み。両方ある場合、どちらも無い場合は書かれていない。
- 判断: `retry-after` を優先。無ければ `reset - 現在秒` を切り上げ、負なら 0。`remaining: 0` だけで手がかりが無いときは 60 秒（GitHub が案内する「少なくとも 1 分」）。現在時刻はテストで固定できるよう `nowMs` オプションにした。
- 実装: `src/lib/github/httpGitHubClient.ts`（`rateLimitFrom`）、`httpGitHubClient.test.ts`。
- 確度: 仮（フォールバックの 60 秒）

### 9. 429 でも、印（`retry-after` か `remaining: 0`）が無ければレート制限にしない

- 状況: 429 は通常レート制限だが、対応表は「403 / 429（`x-ratelimit-remaining: 0` または `retry-after` あり）」。
- 判断: 表のとおり、印の無い 429 は `upstream` / `http`。テストで 403（remaining が 5）と 429（ヘッダー無し）の両方を確かめた。

### 10. 時間切れとネットワーク断の見分け方

- 状況: `AbortSignal.timeout` で中断された `fetch` の例外名に頼るか。
- 判断: 例外の名前でなく `signal.aborted` を見る（MSW 越しでも例外の型が変わっても動く）。MSW の `delay("infinite")` + `timeoutMs: 50` で確かめた。本文の読み取り中に時間切れになった場合は `contract` と判定されるが、扱っていない（GitHub の応答は小さく、可能性は低い）。
- 実装: `src/lib/github/httpGitHubClient.ts`。
- 確度: 確定

### 11. `Deps` と `defaultDeps` はモジュール読み込み時に組み立てる

- 状況: design.md は `defaultDeps` を `withErrorHandling.ts` に置くとだけ書く。`fake` のときの警告は「起動時」。
- 判断: モジュール読み込み時に `createGitHubClient(env, logger)` を呼ぶ。`next build` の「ページデータの収集」でも評価されるため、E2E イメージのビルド中にも警告が 1 回出るが無害。テストは `withErrorHandling` の第 2 引数で差し替えるので、defaultDeps は読み込まれるだけで使わない。
- 実装: `src/lib/api/withErrorHandling.ts`。
- 確度: 確定

### 12. ログのフィールドとメッセージ

- 状況: 8 節は「含めるもの: requestId、ルート、q と page、GitHub のステータス、`x-ratelimit-*`、所要時間」と書く一方、`GitHubError` にステータスやヘッダーは入っていない。
- 判断: ステータスは `detail` の文（「GitHub が 503 を返しました: …」）に含まれる。`x-ratelimit-remaining` / `x-ratelimit-reset` は `retryAfter` に畳まれているので別フィールドでは出さない（`GitHubError` の型を増やす変更になるため）。`q` は 256 文字、`page` は 16 文字で切って記録する（不正な長い入力でログが膨らむのを防ぐ）。`durationMs` は `performance.now()`。
- 実装: `src/lib/api/withErrorHandling.ts`（`logFailure`、`requestFields`）。
- 確度: 仮（`x-ratelimit-*` を別フィールドで残すか）

### 13. 想定外の例外の `detail` にスタックを含めた

- 状況: design.md の疑似コードは `detail: String(e)`。8 節の本文は「元の例外のメッセージ・スタック」。
- 判断: 8 節の本文に合わせ、`Error` なら `e.stack`（無ければ `String(e)`）。production では `respond` が `detail` を落とす。development / test でのみ本文に出る。
- 実装: `src/lib/api/withErrorHandling.ts`、`withErrorHandling.test.ts`（production で漏れないこと、development で出ること）。
- 確度: 確定

### 14. テスト用の入力の作り方

- 状況: `SearchCondition` / `RepoPath` はモデルの parse を通した値しか作らない規約（3 節）。テストごとに parse と失敗時の例外を書くと重複する。
- 判断: `src/test/builders.ts` に `aSearchCondition` / `aRepoPath`（parse に通し、失敗ならテストの書き間違いとして例外）を置いた。
- 確度: 確定

### 15. `expect.stringContaining` が `no-unsafe-assignment` に引っかかる

- 状況: `toEqual({ error: { detail: expect.stringContaining(...) } })` が ESLint の `no-unsafe-assignment`（`any`）で落ちた。最初のコミット（c8571f4）はこの lint 違反を含んだまま作ってしまい、次のコミット（efd1452）で直した。
- 判断: 非対称マッチャを使わず、失敗の種類を `toMatchObject` で、`detail` の文字列は `"detail" in error && error.detail` を `toContain` で確かめる形にした。`as` や `eslint-disable` は使っていない。以降のコミットの前には、変更ファイルに対して ESLint を通してから commit する手順にした。
- 確度: 確定

### 16. テスト環境

- 状況: `vitest.config.ts` の既定は jsdom。MSW と `NextRequest` を使うテストは DOM が不要。
- 判断: これらのテストの先頭に `// @vitest-environment node` を付けた。MSW の lifecycle（listen / reset / close）は共通 setup に入れず、使うテストファイル内に置いた（コンポーネントテストの単位で共通化を判断する）。
- 確度: 確定

## 人間に確認してほしいこと

- 迷った点 1・2・5・8・12 は「仮」。特に 5（`parse.ts` が `lib/model/zodResult.ts` を使うこと）、1（warn の出力先）。
- `docs/design.md` の古い記述: 2 節の `observability/` に `errorReporter.ts` の既定実装（`createLoggerReporter`）が載っていない。4 節の疑似コードは `handleSearch` が `Response` を作らず `Result` を返す形で、実装もそうだが、戻り値の型は `Result<SearchResult, AppError>` / `Result<RepoDetail, AppError>` にした（`Handler` 型の `Result<unknown, AppError>` に代入可）。
- E2E は `bff-errors` の desktop プロジェクトだけ実行した（`docker compose --profile e2e run --rm --build e2e sh -c "npm ci && npx playwright test bff-errors --project=desktop"`）。全件の E2E は流していない。
- Route Handler 2 つ（`src/app/api/search/route.ts`、`src/app/api/repos/[owner]/[repo]/route.ts`）は `withErrorHandling(handler)` を export するだけの組み立てなので、単体テストは書かず E2E に任せた。
