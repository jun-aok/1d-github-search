## 迷った点と判断

### 1. 前の結果を表示している間、件数やページを何の条件で出すか

- 状況: `keepPreviousData` で前の結果を残している間、URL の検索条件は新しいもの、`data` は前の条件の応答になる。新しい条件で `pagination` / `resultRange` を求めると「21〜40 件を表示」と 1 ページ目の行が並ぶ、0 件の案内に新しいキーワードが出る、といった食い違いが起きる
- 選択肢: (a) `queryFn` の戻り値を `{ condition, result }` にして、応答と条件を一緒に持つ (b) `queryFn` は設計どおり `Result` だけを返し、表示中の条件を state で別に追う (c) 食い違いを許す
- 判断: (a)。TanStack Query は placeholder のデータがどのキーのものかを教えてくれないので、応答に条件を持たせるのが一番単純。(b) は描画中に state を直すか ref を使うことになり、読みにくい。設計（5 節）の「`queryFn` は例外を投げず `Result<SearchResult, ApiError>` を返す」の趣旨（例外を投げない、失敗を型付きで data に入れる）は保っている
- 実装: `src/features/search/searchView.ts` の `SearchResponse`、`src/features/search/useSearch.ts` の `queryFn`
- 確度: 仮（設計の記述と形が少し違う）

### 2. ブラウザ側で作る失敗（BFF に届かない、JSON でない、形が違う）の `ApiError`

- 状況: `ApiError` は「モデルのファイル内の関数から作る」規約。`code` は 5 種のどれかにする必要がある
- 選択肢: `UPSTREAM_ERROR` / `INTERNAL_ERROR` / `code` を増やす
- 判断: `lib/model/apiError.ts` に `createClientError(message, detail?)` を足し、`code` は `UPSTREAM_ERROR`、`requestId` なし。画面の分岐（5 節）はレート制限とそれ以外しか見ないので、通信エラーとして出れば足りる。`code` を増やすと BFF の応答の型まで広がる
- 実装: `src/lib/model/apiError.ts`、`src/lib/api/client.ts`。`fetchRepo` を 4 単位目で足せるよう、取得と解析は `getFromBff(path, parse)` にまとめた
- 確度: 仮

### 3. 同じキーワードでの再検索と、覚えている条件への再検索

- 状況: 設計は「検索ボタンを押したら URL が変わらなくても必ず取り直す」。URL が変わらなければクエリのキーも変わらないので、何もしないと取り直さない。60 秒以内に検索した別のキーワードへ戻る場合も、キャッシュが出て取り直さない
- 選択肢: (a) 送信のたびに `invalidateQueries`（キー完全一致）をしてから、条件が違うときだけ `navigate` (b) 同じなら `refetch`、違うなら `navigate` (c) URL に毎回変わる値を足す
- 判断: (a)。表示中のキーなら `invalidateQueries` がその場で取り直し、表示中でなければ古い扱いになって、表示されたときに取り直す。1 つの操作で両方の場合を扱える。同じ条件なら `pushState` しないので、同じ URL の履歴が積み重ならない
- 実装: `useSearch` の `refresh`、`SearchPage` の `onSearch`
- 確度: 確定

### 4. 失敗した結果を覚えない書き方

- 状況: 設計 5 節に「`staleTime` を結果に応じて変える書き方は実装時に確認」とある
- 判断: TanStack Query v5.104 の型定義（`StaleTimeFunction`）で、`staleTime` に `(query) => number` を渡せることを確かめた。成功なら 60 秒、失敗なら 0。失敗した条件へ戻ったときは、失敗の表示を薄くして残したまま取り直す（`refreshing`）。キャッシュから消す方法も考えたが、`refreshing` の扱い（「前の結果がエラーでも同じ」）と矛盾しないのでこれで足りる
- 実装: `src/features/search/useSearch.ts`。`SearchPage.test.tsx` の「成功した結果は覚えて取り直さず、失敗した結果は取り直す」で確かめた（`staleTime` を定数にすると落ちることも確かめた）
- 確度: 確定

### 5. 入力欄の下書きを URL の q に合わせる書き方

- 選択肢: (a) `useEffect` で `setDraft(query)` (b) `SearchForm` に `key={query}` を付けて作り直す (c) 描画中に前回の `query` と比べて state を直す（React の「props の変化に合わせて state を調整する」書き方）
- 判断: (c)。(a) は 1 回古い値で描画され、`react-hooks` の lint にも掛かりやすい。(b) は検索のたびに入力欄が作り直されてフォーカスが外れる
- 実装: `src/features/search/SearchForm.tsx`
- 確度: 確定

### 6. `useSearchUrl` を差し替える方法

- 状況: 設計は「テストではメモリ上で読み書きする偽物に差し替える」。差し替え方は書かれていない
- 選択肢: (a) `vi.mock("./useSearchUrl")` (b) `SearchPage` が `url: SearchUrl` を props で受け、URL と結び付けるのは薄い `SearchPageFromUrl` にする
- 判断: (b)。モジュールのモックが要らず、偽物（`useState` で条件を持つだけの部品）に型が付く。ブラウザバックは `rerender` で条件を差し替えて再現できる。`useSearchUrl` 自体のテストだけは `next/navigation` の `useSearchParams` を `vi.mock` で差し替え、アドレスバー（jsdom の `window.location`）を確かめた
- 実装: `src/features/search/SearchPage.tsx`（`SearchPage` / `SearchPageFromUrl`）、`SearchPage.test.tsx` の `MemoryUrlSearchPage`、`useSearchUrl.test.ts`
- 確度: 確定

### 7. URL に q も page も無いときと、不正なとき

- 判断: `q` と `page` がどちらも無ければ `null`（初期。URL は直さない）。どちらかがあれば `searchConditionFromParams` で解析し、失敗なら `replaceState("/")`。`?page=2` だけのときは「q が無いのに page がある」不正として扱い、E2E の期待（`/` に直す）に合わせた。`?foo=1` のような無関係のパラメータだけのときは `null` になり、URL は直さない
- 実装: `src/features/search/useSearchUrl.ts` の `conditionOf`
- 確度: 確定

### 8. 取得中に前の結果がエラー・0 件・範囲外だったときの「薄く表示」

- 状況: モックの「取得中（前の結果あり）」は一覧だけで、`<ul>` に `opacity-50` と `aria-busy` が付く。エラー・0 件・範囲外を薄くする形はモックに無い
- 判断: 一覧はモックどおり `<ul>` を薄くする。それ以外は取得中だけ `<div class="opacity-50" aria-busy="true">` で包み、取得中でなければ包まない（取得していないときの DOM をモックと同じにするため）
- 実装: `SearchPage.tsx` の `Faded`
- 確度: 仮（見た目の判断。モックに状態を足すかは人間の判断）

### 9. 範囲外ページの「空の一覧」

### 10. `error.tsx` の `reset` と `retry`

- 状況: 設計 8 節は `reset()`。Next.js 16.4 の同梱ドキュメント（`file-conventions/error.md`）では `retry` が 16.3 で安定版になり、`reset` より `retry` を勧めている
- 判断: `retry` を使う。描画を作り直すだけでなく取り直しもするので、「再試行」の意味に合う
- 実装: `src/app/error.tsx`、`src/app/global-error.tsx`、共通の中身は `src/components/UnexpectedError.tsx`
- 確度: 仮（設計の記述の更新が要る）

## 人間に確認してほしいこと

1. **モック比較（検索）の 4 件が通らない（モックとテストの食い違い）**: `dom-compare-search.spec.ts` のレート制限・通信エラーの状態（A・B の 2 件ずつ）。違いは入力欄の値だけで、モック（`mock/search.html` の `show()`）は `ratelimit` / `error` で `q.value = "react"`、実装は URL の `q`（`__rate_limited__` / `__error__`）を出す。入力欄を URL の `q` に合わせることは `search-url.spec.ts`・`navigation.spec.ts`・設計 5 節が求めているので、実装では両立できない。直すならモックの `show()` で `ratelimit` → `"__rate_limited__"`、`error` → `"__error__"` にする（`empty` / `few` と同じやり方）。それ以外のクラス構成・文言・属性は一致している
2. `queryFn` の戻り値を `{ condition, result }` にした（迷った点の 1）。設計 5 節の記述の更新が要るか
3. ブラウザ側の失敗の `code` を `UPSTREAM_ERROR` にした（迷った点の 2）
4. `error.tsx` は `retry` を使った（迷った点の 10）。設計 8 節の `reset()` の記述
5. 取得中のエラー・0 件・範囲外の薄い表示の形（迷った点の 8）
6. `not-found.tsx` は文言をモックが無いので仮に「ページが見つかりません」+「検索ページへ戻る」にした（E2E の対象外）
