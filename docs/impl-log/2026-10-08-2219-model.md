## 迷った点と判断

### 1. fixture をそのまま parse できるテストを書かなかった

- 状況: 依頼に「fixture（`src/mocks/fixtures/*.json`）の形をそのまま parse できることも 1 件」とある。しかし fixture は GitHub の生の JSON（`stargazers_count`、`html_url`、`owner.avatar_url`、`fullName` なし）で、モデルの JSON の形（`stars`、`url`、`owner.avatarUrl`、`fullName`）とは項目名が違う。`parseRepoDetail` にそのまま渡すと必ず失敗する。
- 選択肢: (a) テスト内で項目名を写してから `parseRepoDetail` に渡す。(b) 写す処理は `lib/github/parse.ts`（design.md 4 節）の担当なので、このテストはそちらの単位に回す。
- 判断: (b)。(a) はテスト内に `parse.ts` 相当の変換を手書きするだけで、本物の変換を確かめない。設計では「fixture の生 JSON → `github/parse.ts` → モデルの `parse`」の 2 段なので、通しのテストは `github/parse.ts` の単位で書くのが筋。代わりに `repo.test.ts` は facebook/react に近い値、`searchResult.test.ts` は合成した 20 件（`description` / `language` が null のものを含む）を使っている。
- 実装: なし（テストを書いていない）。
- 確度: 仮（依頼の指示を満たしていない。人間の確認が要る）

### 2. zod を使うモデルのファイルに共通の詰め替え関数を置いた（`zodResult.ts`）

- 状況: `ZodError` を `ParseError` に詰め替える処理が、`searchCondition`・`repoPath`・`repo`・`searchResult`・`apiError` の 5 か所に要る。
- 選択肢: (a) 各ファイルに同じ 5 行を書く。(b) `lib/model/zodResult.ts` に `safeParse(schema, input)` を 1 つ置き、各ファイルが使う。
- 判断: (b)。詰め替え方（`path` を `.` でつなぐ）が食い違うのを防ぐ。`safeParse` の引数は zod のスキーマ型だが、これを使うのは `lib/model/` 内のファイルだけで、`lib/model/` の外へは何も再エクスポートしていない（`model/index.ts` も作っていない）。依頼の「スキーマを export しない」には、スキーマ自体は触れていない。ただし「zod の型を外に出さない」を `lib/model/` 内のファイル間まで含めると読むなら、これは抵触する。
- 実装: `src/lib/model/zodResult.ts`。
- 確度: 仮

### 3. `SearchResult` の `items` は `RepoSummary` のスキーマを使い回さず、`parseRepoSummary` を呼ぶ

- 状況: `SearchResult` は `items: RepoSummary[]` を持つが、`RepoSummary` のスキーマは export しない決まり。
- 選択肢: (a) `repo.ts` からスキーマを export して `searchResult.ts` で `z.array(summarySchema)` と書く。(b) `z.custom<RepoSummary>(v => parseRepoSummary(v).ok)` を使う。(c) `items` は `z.array(z.unknown()).max(20)` で外形だけ確かめ、各要素を `parseRepoSummary` に通して失敗を集める。
- 判断: (c)。(a) はスキーマの export 禁止に反する。(b) は失敗の `path` が `items.1` で止まり、`items.1.stars` のように中が分からない。(c) は `path` を `items.<番号>.<項目>` に組み立てられる。代償は、`SearchResult` の型を `z.infer` からでなく `DeepReadonly<{ totalCount: number; items: RepoSummary[] }>` と手書きになること（依頼の「型は `DeepReadonly<z.infer<…>>`」から外れる）。zod の型と手書きの型の食い違いはテストで検出される範囲（`parseSearchResult` の戻り値の型が合わなければ typecheck が落ちる）。
- 実装: `src/lib/model/searchResult.ts`。
- 確度: 確定

### 4. `Pagination` の形（「前後の有無」ではなく前後のページ番号）

- 状況: 依頼は「現在ページ、総ページ数、前後の有無。範囲外のときの『前へ』は最終ページへ」。有無だけ（`hasPrev` / `hasNext`）だと、「前へ」の行き先が範囲外のとき最終ページになる規則を、呼び出し側が再実装することになる。
- 選択肢: (a) `{ page, totalPages, hasPrev, hasNext }` と、行き先を返す別関数。(b) `{ page, totalPages, prevPage: number | null, nextPage: number | null }`。`null` が「移れない」。
- 判断: (b)。有無は `!== null` で分かり、行き先の規則が `pagination` 1 か所に閉じる。0 件のときは `prevPage` も `null`（最終ページが無いため）にした。
- 実装: `src/lib/model/pagination.ts`（`Pagination` 型）。
- 確度: 仮（PaginationNav を作る側が `hasPrev` / `hasNext` を期待しているなら調整が要る）

### 5. 件数表示の関数名を `resultRange` にした

- 状況: 依頼は「件数表示の a・b」とだけあり、関数名の指定がない。
- 判断: `resultRange(condition, itemCount): { from, to }`。`from = (page-1)*20+1`、`to = (page-1)*20+itemCount`。範囲外ページ（0 件）では `from > to`（例: ページ 10 で 181 と 180）になるが、式のとおりにして、表示するかどうかは画面側の判断とした（5 節の「範囲外」の表示は件数を出さない可能性がある）。
- 実装: `src/lib/model/pagination.ts`。
- 確度: 仮（名前）

### 6. `parseRepoPath` の入力は `{ owner, repo }`、出力は `{ owner, name }`

- 状況: design.md の 3 節の境界の表は「`{ owner, repo }` → `RepoPath`」、一覧は `RepoPath` の中身を `owner`・`name` としている。4 節の `handleRepo` は `parseRepoPath(await ctx.params)` と書かれている。
- 判断: 入力の項目名は `repo`（Next.js の `params` のキーがそのまま入る）、出力は `name`。zod の `.transform` で写した。依頼の「`RepoPath`（owner、name）」とも合う。
- 実装: `src/lib/model/repoPath.ts`。
- 確度: 確定

### 7. `searchConditionFromParams` で `page` の形式違いを `parseSearchCondition` に断らせた

- 状況: `page` は `^[1-9][0-9]*$` のみ。`Number("02")` は 2 になるので、先に正規表現で確かめる必要がある。形式に合わない場合に自前で `fail` を作ると、`ParseError` の `path`・`message` を二重に持つことになる。
- 判断: 形式に合えば `Number` で数値に、合わなければ文字列のまま `parseSearchCondition` に渡す。スキーマの `z.number()` が `path: "page"` で断る。省略（`null`）は 1。
- 実装: `src/lib/model/searchCondition.ts`。
- 確度: 確定

### 8. `retryAfter` は 0 以上の整数にした

- 状況: design.md の `ApiError.retryAfter` は「秒」としか書かれていない。
- 判断: 4 節のエラー対応表で「`retry-after` か `x-ratelimit-reset` までの秒数。0 未満は 0」なので、0 以上の整数とした。BFF が小数の秒を返す実装にすると、ブラウザ側の `parseErrorResponse` が弾くので注意（切り上げて整数にする前提）。
- 実装: `src/lib/model/apiError.ts`。
- 確度: 仮

### 9. `avatarUrl` が URL として読めない文字列を受け取ったときの扱い

- 状況: `new URL` は読めない文字列で例外を投げる。ただし入力は `parseRepoSummary` を通った https の URL のはずで、通常は起きない。
- 選択肢: (a) 例外を投げる（型安全の原則 4「例外を投げず Result」に反する）。(b) `Result` を返す（呼び出し側のコンポーネントが毎回 `Result` を扱うことになり、起きない失敗のために重い）。(c) そのまま返す。
- 判断: (c)。`URL.canParse` で確かめ、読めなければ入力をそのまま返す。
- 実装: `src/lib/format.ts`。
- 確度: 仮

### 10. テスト側の誤り: `new URLSearchParams({ q: "%20%20" })`

- 状況: 「q が空白のみなら失敗する」のテストで、空白を `"%20%20"` と書いたところ、`URLSearchParams` のオブジェクト形式は値をデコードしないので、`q` は文字どおり `"%20%20"`（非空白の 6 文字）になり、`ok: true` で通ってしまった。
- 判断: 実装の問題ではなくテストの誤りなので、テストの値を `"  "`（半角空白 2 つ）に直した。期待値は変えていない。
- 実装: `src/lib/model/searchCondition.test.ts`。
- 確度: 確定

### 11. Red が「期待値の違い」にならない場合

- 状況: `ok` / `fail` の最初のテストは、スタブを `throw new Error("not implemented")` にしたため、Red の失敗が「not implemented の例外」だった（workflow.md は期待値の違いでの失敗を求めている）。
- 判断: 以降のスタブは、型を通しつつ値が違う戻り値（`fail({ issues: [] })`、`-1` など）にして、アサーションの失敗で Red を確かめた。`ok` / `fail` はそのまま実装して進めた（2 行で、振る舞いがほぼ自明）。

### 12. 先に実装が通ってしまうテスト

- 状況: 次の追加テストは、書いた時点で Green だった。直前の Green の実装が、すでにその振る舞いを満たしていたため（スキーマの形を決めた時点で決まる振る舞い）。
  - `parseSearchCondition` の失敗の `path`・`message`、`null` や文字列の入力
  - `searchConditionFromParams` の基本ケース以降のうち、境界（0・1・50・51・空）
  - `RepoSummary` の欠けた項目、`description`/`language` が null
  - `apiError` の code が 5 種のとき、知らない code、`message` 欠け
  - `repoPath` の「通すもの」
- 判断: テストは残した（回帰を防ぐため）。Red にならなかったことは、サイクルの記録に「Green のまま追加」と書いた。
