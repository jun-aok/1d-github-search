## 迷った点と判断

### 1. 詳細のアイコンに `loading="lazy"` を付けるか

- 状況: `docs/design.md` 6 節は、アイコンの `<img>` に `width` / `height` と `loading="lazy"` を付けるとしている。一方 `mock/detail.html` の `<img id="avatar">` には `loading` が無く、E2E の DOM 比較（`e2e/dom-compare-detail.spec.ts`）は属性まで比べる
- 選択肢: (a) 設計どおり付ける → DOM 比較が落ちる。(b) モックどおり付けない → 設計の文と食い違う
- 判断: (b)。e2e/ と mock/ は変えない指示で、DOM 比較が「モックどおり」の判定基準のため。詳細のアイコンは画面の最上部に 1 枚だけで、遅延読み込みの利点もほぼ無い
- 実装: `src/features/repo/RepoDetailView.tsx`
- 確度: 仮（設計 6 節の文を「一覧のみ lazy」に直すか、モックに足すかの判断が要る）

### 2. `page.tsx` を Server Component にするか Client Component にするか

- 状況: `docs/design.md` 4 節に「Client Component のページでは `use(params)` か `useParams()` で受ける」とあり、5 節の構成図は `page.tsx └ RepoDetailPage (client)` になっている
- 選択肢: (a) `page.tsx` に `"use client"` を付けて `use(params)`。(b) `page.tsx` は検索ページの `app/page.tsx` と同じく Server Component のままにし、`await params` で取り出した `{ owner, repo }` を Client Component の `RepoDetailPage` に渡す。(c) `RepoDetailPage` の中で `useParams()`
- 判断: (b)。`await params` はデータ取得ではない。`RepoDetailPage` が `{ owner, repo }` を props で受ければ、コンポーネントテストで Next.js のルーターを偽物にせずに済む（(c) だと `next/navigation` の差し替えが要る）。`app/page.tsx` と書き方も揃う
- 実装: `src/app/repos/[owner]/[repo]/page.tsx`、`src/features/repo/RepoDetailPage.tsx`（`RepoParams` 型）
- 確度: 確定（4 節の記述は「Client Component にするなら」の条件付きと読んだ）

### 3. `params` の値は URL の符号化が残ったまま届く

- 状況: 開発サーバーで `/repos/a%20b/x` を開くと、SSR の HTML がスケルトン（= `parseRepoPath` を通った）になった。`params.owner` は `a b` ではなく `a%20b` のまま届いている（Next.js 16.4 で確認）。`fetchRepo` は各部を `encodeURIComponent` するので、`a%2520b` として BFF に送られる
- 選択肢: (a) `page.tsx` で `decodeURIComponent` する（不正な `%` で例外になるので `Result` に包む必要がある）。(b) そのまま
- 判断: (b)。設計に復号の記述が無く、仕様を自分で決めない。GitHub の owner / repo 名は英数字と `.` `_` `-` だけなので、実在するリポジトリの表示には影響しない。符号化された文字を含むパスは、二重に符号化されても GitHub が 404 を返し、どちらでも「見つかりません」になる
- 実装: 変更なし
- 確度: 仮（BFF の Route Handler の `params` も同じく符号化されたままかは確かめていない。設計で扱いを決めてほしい）

### 4. 再試行中（エラー表示から取り直している間）の見せ方

- 状況: 検索ページは取得中に前の表示を薄くする（`Faded`）が、詳細ページの再試行中については設計に記述が無い
- 選択肢: (a) 何もしない（エラー表示がそのまま残り、結果が返ると替わる）。(b) 検索と同じく薄くする。(c) スケルトンに戻す
- 判断: (a)。設計に無いものは足さない。E2E の「再試行ボタンを押すと、もう一度取得する」もエラー表示が残ることを前提にしている
- 実装: `src/features/repo/RepoDetailPage.tsx`（`useRepo` は `isFetching` を返していない）
- 確度: 仮（薄くするかどうかは人間の判断）

### 5. 状態の判定を純粋関数（検索の `searchView` のような）に分けるか

- 状況: 検索ページは画面の状態を判別共用体で求める `searchView` を持つ。詳細ページは「パス不正 / 取得中 / NOT_FOUND / その他の失敗 / 成功」の 5 通りだけ
- 選択肢: (a) `repoView` を作る。(b) `RepoDetailPage` の中で順に `if` で分ける
- 判断: (b)。前の結果の保持や範囲外など、検索ページで純粋関数に切り出した理由になった込み入った条件が無い。レート制限と通信エラーの出し分けは `ErrorMessage` が `code` で行う。範囲外の部品を足さない
- 実装: `src/features/repo/RepoDetailPage.tsx`
- 確度: 確定

### 6. 詳細のスケルトンの置き場所

- 状況: `docs/design.md` 2 節は `Skeleton` を `components/`（画面共通）に置く。既存の `ListSkeleton` は検索の一覧の形
- 判断: 同じ `src/components/Skeleton.tsx` に `DetailSkeleton` を足した。クラス構成は `mock/detail.html` の読み込み中のまま（`mt-6` も `aria-live` も無い）
- 確度: 確定
