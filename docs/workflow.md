# 作業ルール

## 開発の進め方

「完成するまで開発を止めない」ループを回す。完成の定義は「lint と型チェックが通り、単体テストと E2E（production ビルドを含む）がすべて Green」。
テストの Red / Green は開発中の状態にすぎず、ループが終わったときに Green であればよい。

### ループの前（人が確認する段階）

1. 要件・設計を固める（`docs/requirements.md`、`docs/design.md`）
2. 初期セットアップと**スパイク**: プロジェクトを作り、設計で「実装時に確認」とした Next.js 16 の挙動（`pushState` を `useSearchParams` が検知するか、`next.config.ts` から `env.ts` を読めるか、E2E 一式の所要時間が Stop フックの 900 秒に収まるか、など）を小さなコードで確かめ、結果を `docs/design.md` に反映する
3. **E2E テスト（Playwright）をすべて書く**。要件の各項目に対応する画面の操作と結果を、コードとして定義する。モックとの DOM 比較（`docs/design.md` 7 節）も含める。モックのリンク先とデータを E2E に合わせて直すのもこの段階。この時点ではすべて Red
4. ユーザーが E2E テストをレビューする（「これが全部通れば完成」と言えるか）
5. ユーザーがループ開始を宣言し、`.claude/loop-active` を作る（Stop フックが E2E を完成判定に含める合図。Git には含めない）

単体テストはこの段階では書かない → 理由: 単体テストはコードの内部構造に依存するので、実装前に全部書くと設計の前提が違ったときに書き直しになる。E2E は画面の操作と結果しか見ないので先に書ける

### ループの中（二重ループ）

```
外側: Red の E2E テストを 1 グループ（docs/test-cases-e2e.md の節、または実装順序の 1 単位）選ぶ
   内側: 単体テストを 1 件書く → 実装 → Green → リファクタリング → コミット … を繰り返す
   その E2E が Green になったら、code-reviewer にレビューさせる（下記）
外側: 「必ず直す」指摘が無くなったら次のグループへ。すべて Green になったら全体レビュー → README → 完成
```

内側の 1 サイクル（Kent Beck の手順）:

1. これから作る振る舞いを 1 つ選び、テストを 1 件書く
2. コンパイルを通す。テストが参照する関数や型を、中身の無い形（`throw new Error("not implemented")`）で用意する。型チェックのフックはこの段階を飛ばせないようにしている
3. テストを実行し、**期待値の違いで**失敗することを確認する（Red）
4. そのテストを通す最小の実装を書く（Green）。先回りして他の機能を作らない
5. テストが通った状態を保ちながら、重複や命名を整える

振る舞いを選ぶ順は「正常系の最も単純なケース → 境界値 → エラー系」。設計で決めた関数の分け方（`docs/design.md`）に沿う

### レビュー（外側のループ 1 周ごと）

E2E が 1 グループ Green になるたびに、`code-reviewer` エージェントにレビューさせる。最後にすべて Green になったら、差分ではなく全体を対象にもう 1 回行う。

1. 範囲: 前回のレビュー以降の差分（初回はセットアップ以降すべて）。全体レビューは `src/` と `e2e/` 全体
2. レビュアーはコードを直さない。指摘を返し、直すのは実装担当
3. 指摘の扱い

   | 区分 | 扱い |
   | --- | --- |
   | 必ず直す（設計との不一致、型安全の抜け道、テストが何も確かめていない、秘密情報やエラー詳細の漏れ） | 直してから次へ進む。直したら再レビュー。「必ず直す」が無くなるまで繰り返す |
   | 直した方がよい | 直す。見送る場合は理由を impl-log に書く |
   | 軽微 | 記録だけ |

4. 結果を `docs/review-log/<日付>-<グループ名>.md` に記録する（指摘の一覧、対応、見送った理由）
5. ユーザーには、外側のループ 1 周ごとに、レビューの要約と「必ず直す」が無くなったことを報告する

### 完成の判定（Stop フック）

応答を終えるとき、`.claude/hooks/test.sh` が次を順に実行し、失敗があれば差し戻す。実行はすべてコンテナ内（`docker compose run --rm app npm run …`、E2E は `docker compose --profile e2e`）で、ホストには Node.js を置かない。Docker デーモンが動いていなければ、その旨を伝えて差し戻す。

1. `npm run lint`
2. `npm run typecheck`
3. `npm test`（単体・コンポーネント）
4. `npm run test:e2e`（`.claude/loop-active` があるときだけ。1〜3 が通ってから）

差し戻しが 5 回連続したら、無限ループを防ぐために警告を出して通す。回数はユーザーの発言と成功でリセットされる

### 何をどのレベルでテストするか

| 対象 | テストの種類 | ツール |
| --- | --- | --- |
| 純粋なロジック（モデルの解析、総ページ数、応答の変換表） | 単体テスト | Vitest |
| `HttpGitHubClient` | 単体テスト。GitHub は MSW でモック | Vitest + MSW |
| Route Handler の各処理 | 単体テスト。`GitHubClient` を偽物に差し替え | Vitest |
| コンポーネント・ページ（状態ごとの表示、操作） | コンポーネントテスト。BFF は MSW でモック | Vitest + Testing Library + MSW |
| 画面をまたぐ流れ（検索 → 一覧 → 詳細 → 戻る、エラー表示、モバイル幅） | E2E。production ビルド + `GITHUB_CLIENT=fake` | Playwright |

### テストの対象外

- プロジェクトの初期セットアップ、設定ファイル（`next.config`、`tsconfig`、ESLint 等）
- 見た目だけの調整（余白・色・レイアウト）。ただし「表示される / されない」「無効化される」などの振る舞いは対象
- 型定義のみのファイル

### 禁止事項

- テストを通すためにテスト側を弱める（期待値を実装に合わせる、`skip` / `only` / `todo` にする、アサーションを削る、E2E を消す）
- 実装の都合で振る舞いと無関係なテスト（内部構造・private な関数）を書く
- `.claude/loop-active` を自分で作る・消す（ユーザーだけが操作する）

### コミット

- ループ中は AI が自律的にコミットしてよい。内側の 1 サイクル（Red → Green → Refactor）ごとに 1 コミット。コミットメッセージはテストが表す振る舞いを書く（例: `検索キーワードが空のときは検索ボタンを無効化する`）
- 単体テストが Red のままコミットしない（E2E が Red なのは途中の状態なので構わない）

## 一般

- コミットは意味のある単位で小さく分ける。push はユーザーの指示があったときだけ行う
- 要件にない機能を勝手に追加しない。追加したい場合は先に提案する
- 設計判断をしたときは、理由を `docs/design.md` の該当箇所に「→ 理由:」として残す（README の「選択理由」の元ネタ）
- 技術スタックを変更・追加したときは、`CLAUDE.md` の表と README の「選択理由」を同時に更新する
- シークレットをコミットしない。環境変数は `.env.local` に置き、`.env.example` を用意する
- コード中のコメントと README は日本語、識別子は英語
